## Context

Once a request is accepted, the owner and the applicant talk inside Patas to get to
know each other and arrange the handover, without sharing contact details. A message
must reach an open conversation at once, and on any other page a toast must link to
the conversation. When the request ends, the conversation stays readable but nobody
can write.

The browser never calls FastAPI directly (ADR 0005). The frontend runs on Vercel
(serverless functions with a maximum duration) and the backend on Render (one
process).

## Decisions

1. **`Message` is its own aggregate; the request's State decides when one can be
   written.** `AdoptionApplication.post_message` checks that the writer is one of the
   two sides (anyone else gets a 404, like the other adoption endpoints), then
   delegates to the state. Only `AcceptedState` creates the message and records
   `MessagePosted`; every other state refuses (409 `conversation_closed`). The request
   never loads its messages. A message is trimmed, 1 to 2000 characters, and never
   edited or deleted; the `messages` table (migration `0014`) repeats the rule.
2. **`accepted_at` says who can read.** The request records when it was accepted
   (migration `0013`, with a CHECK: accepted and adopted requests always have it, open
   and closed ones never do). The two sides can read the conversation of a request
   that was accepted at some point, also after it ended. A request declined or
   withdrawn while still open never had one.
3. **Endpoints.** `GET /applications/{id}/messages?after=<message id>` returns the
   conversation in `(sent_at, id)` order, or only the messages after that one.
   `POST /applications/{id}/messages` writes one, taking the locks in the order of
   ADR 0017, decision 8, so a message never lands after a decline. There is no
   `GET /applications/{id}`: the page keeps finding the request in the two request
   lists, which now carry `accepted_at`.
4. **Live updates go through Ably, on one channel per person, `user:<id>`.** After the
   commit, a `LiveAnnouncer` (Observer: after-commit handlers) tells both sides about
   `message.posted` and `request.changed` (a request declined or withdrawn after being
   accepted, or adopted). A notice carries ids and names, **never the text**: the page
   fetches the message from Patas. A failed publish is logged and never undoes the
   change. Without `ABLY_API_KEY`, a `NullPublisher` is used and the browser does not
   connect: everything works, only not live.
5. **The browser listens with a token that can only subscribe to its own channel.** The
   Route Handler `/api/ably/token` checks the session and issues a token request with
   `capability: { "user:<id>": ["subscribe"] }`; the API key never leaves the server.
   One connection per tab lives in the root layout and hands every event to a small
   client-side bus (Observer). The chat listens there, and other pages show a toast.
   After a reconnection the chat fetches what it missed with `after`.
6. **Ably's side-specific packages.** The account is billed by monthly active users,
   which refuses the plain `ably` package (error 40168). The backend publishes with
   `ably-pubsub-server`, the token route signs with `@ably/pubsub-server`, and the
   browser listens with `@ably/pubsub-device`, so only people count as users.
7. **The conversation page** has a compact header with the guidelines closed, then the
   chat beside the handover checklist, which collapses into a tab on the chat's edge.
   On small screens the checklist is a button above the chat.

## Alternatives considered

* **Own WebSocket from the browser to FastAPI, with an in-memory hub:** real time with
  no third party, and the live path testable in pytest. But it is an exception to ADR
  0005 (CORS, an origin check, a token in the browser), works only with one process,
  and needs reconnect and token-expiry code; how Render treats idle connections was
  also unknown.
* **Server-Sent Events through a Next Route Handler:** keeps ADR 0005, but Vercel
  functions have a maximum duration, and every open tab holds a running function.
* **Pusher:** a similar hosted service with a similar free plan; the `LivePublisher`
  interface lets it replace Ably. Ably's integration was smaller here (an async Python
  SDK, the permission carried by the token).
* **Polling:** not real time, which the story asks for.
* **A `Conversation` aggregate with its own open/closed status:** it duplicates the
  request's status, so two places would say "ended", kept in step by handlers.

## Pending team agreement

`AGENTS.md` section 6 asks for business rules to be agreed with the team before they
are implemented. The code already follows these proposals:

* The Ably account: who owns it, and one app per environment (development, staging,
  production) with its `ABLY_API_KEY` in Render and Vercel.
* The 2000-character limit, no editing or deleting, and no system messages ("Ana
  accepted the request").
* The messages stay after the request ends; how long they are kept is still open
  (AdoptionPipeline D6).

## Consequences

* (+) The rule "only while accepted" lives in the State pattern; the database repeats
  the message rules and the `accepted_at` invariant. The adoption code does not know
  Ably exists.
* (+) US-32 (in-app notifications) can reuse the same channel and events, and US-22
  (photos) adds a kind of message behind the same State rule.
* (−) A third-party dependency with free-plan limits (200 connections, about 6 million
  messages a month), and its key in two environments.
* (−) AT-24's "without reloading" is automated up to the publisher (a recording one in
  the tests). Delivery by Ably is checked by hand in a browser.
